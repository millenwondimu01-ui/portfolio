A Critical Review of a Credit Card Fraud Detection Project

For this assignment, I reviewed a credit card fraud detection study by Albalawi and Dardouri (2025). I chose this project because fraud detection involves more than building a model with a high accuracy score. A financial institution also must think about missed fraud, false alerts, customer privacy, and how the model will continue working as fraud patterns change. The study did several things well, especially in handling imbalanced data, but I also noticed areas that would need more attention before using the system in a real financial environment.

The researchers used a public credit card dataset containing 284,807 transactions. Only 492 transactions were fraudulent, which was about 0.17% of the dataset. This created a serious imbalance because almost all the transactions were legitimate. The team began by removing duplicate records, checking for missing values, standardizing the data, and selecting useful features. After duplicates were removed, 283,726 transactions remained. Most of the features were already anonymized through principal component analysis, which provided some protection for customer information.

The class imbalance was the biggest data issue in the project. If a model predicted that every transaction was legitimate, it could still appear highly accurate. To address this problem, the researchers used SMOTE to create additional examples of the fraud class. They applied it to the training data instead of the entire dataset. I think this was an important decision because applying SMOTE before separating the test data could cause data leakage. However, the article was not completely clear about whether every other preprocessing step was also completed after the split. I would want that process documented more carefully because even a small amount of leakage could make the results look better than they really are.

Instead of depending on one algorithm, the researchers compared logistic regression, decision tree, random forest, XGBoost, and an improved deep-learning model. Each model served a different purpose. Logistic regression offered a simpler baseline that was easier to explain. Decision trees could capture relationships that were not linear, while random forest combined multiple trees to produce more stable predictions. XGBoost provided another strong ensemble model. The deep-learning model used dropout, batch normalization, and focal loss. Focal loss was especially useful because it placed more attention on difficult fraud cases.

The traditional models were tuned using grid search. The deep-learning model used early stopping and learning-rate reduction to control overfitting. The final evaluation included accuracy, precision, recall, F1-score, ROC-AUC, and confusion matrices. Using several metrics was one of the strongest parts of the project. In fraud detection, accuracy does not tell the entire story. Recall shows how much actual fraud was detected, while precision shows how many fraud alerts were correct. F1-score helps show the balance between them. Google (2026) explains that accuracy can be misleading when one class greatly outnumbers another.

One issue I noticed was that the reported results were not fully consistent. The abstract stated that random forest achieved 99.95% accuracy, an F1-score of 0.8256, and a ROC-AUC of 0.9759. However, one of the results tables reported 99.69% accuracy, an F1-score of 0.7442, and a ROC-AUC of 0.9997 for the same model. Different sections also seemed to disagree about whether random forest or deep learning performed best overall. Before recommending any model for deployment, I would first reproduce the results and confirm that the tables, discussion, and conclusion all match. This reminded me that good documentation is part of model verification. Strong numbers are not useful if the team cannot explain exactly how they were produced.

The project addressed privacy to some extent because the transaction features were anonymized. Still, I do not think anonymization by itself is enough. A false positive could block a legitimate purchase and create stress for the customer. A false negative could allow actual fraud to continue. The model should therefore support human review instead of making every high-impact decision automatically.

The study handled imbalance in the data, but it did not provide much analysis of fairness among different customer groups. Since most features were anonymized, it would also be difficult to determine whether certain groups experienced more false alerts than others. NIST (2023) states that trustworthy AI should be reliable, privacy-enhanced, transparent, and fair. If I were working on this project, I would test error rates across any legally and ethically available customer or transaction segments. I would also create a clear appeal process for customers whose legitimate transactions were blocked.

The article discussed prediction speed and whether the models could operate in real time, but it did not provide a detailed monitoring plan. That is a major weakness because fraud methods constantly change. After deployment, I would monitor recall, precision, F1-score, false-positive rates, and changes in transaction patterns. I would review these measures weekly and compare them with the original baseline. Confirmed fraud cases and customer complaints could help identify new patterns. A serious performance decline or major data drift would trigger further review and possible retraining.

My main takeaway from this case is that model accuracy should never be reviewed alone. A fraud model must catch suspicious activity without creating too many problems for legitimate customers. I would apply the study’s use of multiple models, class-imbalance treatment, and several evaluation metrics in future projects. At the same time, I would improve the documentation, fairness testing, and monitoring plan before considering the model ready for real-world use.
